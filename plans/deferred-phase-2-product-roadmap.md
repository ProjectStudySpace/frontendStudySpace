Product expansion remains deferred until the stabilization-only [final acceptance gate](phase-2-contract-stabilization-status.md#final-stabilization-acceptance-gate) passes. This document owns work after stabilization: intraday product UI, push integration, gamification runtime validation, onboarding/i18n, and deferred product end-to-end journeys. It does not define Units 3–9 and does not imply that any workstream below is implemented.

## Review path

## Workstream 1: Intraday review UI

### Outcome

Users can discover, open, complete, and understand intraday reviews generated by intensive study.

### Existing foundation

- `src/types/intradayReviews.ts`
- `hooks/useIntradayReviews.ts`
- intraday review data displayed in parts of the intensive-session result model

### Required work

- Create `src/components/IntradayReviewCard.tsx`.
- Create `src/pages/IntradayReviewPage.tsx`.
- Register the protected `/intraday-reviews` route and unauthenticated redirect.
- Add a pending-review entry point to `src/components/spacedRepetitionDashboard.tsx`.
- Connect post-session results to the intraday route where product behavior requires it.
- Add focused English and Spanish strings for the implemented flow.
- Align UI states with backend `SCHEDULED`, `NOTIFIED`, `ACTIVE`, `COMPLETED`, `SKIPPED`, and `EXPIRED` semantics before implementation.

### Acceptance checklist

- [ ] List, active-review, completion, empty, loading, and error states are defined.
- [ ] Route protection matches existing protected pages.
- [ ] Backend status transitions are represented without lossy frontend-only assumptions.
- [ ] Review completion handles authoritative errors and refreshes the list.
- [ ] Dark mode and keyboard interaction are reviewed.
- [ ] Focused component and flow tests pass.

## Workstream 2: Push notification integration

### Outcome

Users can explicitly enable or disable browser push notifications and navigate from a notification to a valid product destination.

### Existing foundation

- `src/types/pushNotifications.ts`
- `hooks/usePushNotifications.ts`
- push-related translation keys

### Required work

- Add and review the service worker at the Vite public-asset location.
- Handle `push` and `notificationclick` events.
- Add permission and subscription controls to `src/pages/Settings.tsx`.
- Verify VAPID key retrieval, subscription, unsubscription, and browser capability handling.
- Route notification actions only to implemented destinations.
- Define behavior for denied permission, revoked subscriptions, unsupported browsers, and stale endpoints.

### Acceptance checklist

- [ ] Subscription is initiated only by explicit user action.
- [ ] Permission denial is recoverable and clearly explained.
- [ ] Unsubscription updates browser and backend state consistently.
- [ ] Notification clicks focus an existing window or open a safe route.
- [ ] Intraday notification links are enabled only after the route exists.
- [ ] Browser-level verification is recorded separately from hook tests.

## Workstream 3: Gamification runtime validation

### Outcome

The existing gamification page renders authoritative backend data correctly without duplicated layout, field fallbacks that hide contract drift, or misleading empty states.

### Existing foundation

- `src/pages/GamificationPage.tsx`
- `hooks/useGamification.ts`
- `src/types/gamification.ts`
- `src/components/gamification/`
- protected `/gamification` route and navigation entry

### Required work

- Verify stats, badges, leaderboard, level progress, XP transactions, and multipliers against current backend responses.
- Recheck historical duplicated-layout behavior against current code.
- Identify compatibility mappings and decide whether they belong in a contract adapter.
- Validate loading, empty, authorization, pagination, and backend-failure states.

### Acceptance checklist

- [ ] Runtime payloads match documented adapters or types.
- [ ] No duplicated protected layout is rendered.
- [ ] Leaderboard pagination and current-user position are verified.
- [ ] Badge names and descriptions match implemented backend badge identifiers.
- [ ] No additional gamification scope is added during validation.

## Workstream 4: Onboarding and i18n

### Outcome

Settled Phase 2 flows are discoverable and consistently described in English and Spanish.

### Required work

- Add onboarding steps only for implemented, stable routes.
- Add an intensive-study page guide if usability review supports it.
- Complete intraday and push strings after those experiences are implemented.

### Acceptance checklist

- [ ] English and Spanish namespaces have equivalent keys.
- [ ] No copy promises deferred or unavailable behavior.
- [ ] Error messages preserve actionable backend context without exposing internals.

## Workstream 5: Deferred product end-to-end validation

### Outcome

After stabilization and the preceding roadmap workstreams are implemented, the expanded Phase 2 product journeys are verified across intraday review, push, gamification, onboarding, and persistence boundaries.

The intensive/Pomodoro create/start/block/card/break/reload/error/abandon flows belong to the stabilization gate and are prerequisites here, not deferred workstream deliverables.

### Priority journeys

1. Complete a stabilized intensive session and discover its resulting intraday reviews.
2. Complete an intraday review and observe authoritative state and rewards.
3. Enable push, receive a notification, navigate to an implemented destination, and unsubscribe.
4. View gamification data after stabilized intensive and intraday activity.
5. Complete onboarding and translated navigation across only implemented Phase 2 routes.
6. Recover the expanded product journey after authentication expiry or a degraded dependency without invalidating the already-passed stabilization contract.

### Acceptance checklist

- [ ] The stabilization gate remains green and is referenced rather than duplicated here.
- [ ] Tests use documented backend fixtures or a controlled real environment.
- [ ] Authentication expiry and degraded network states are included at the deferred feature boundaries.
- [ ] Real PostgreSQL persistence is verified for critical deferred transitions when authorized.
- [ ] Browser-specific push behavior is recorded.
- [ ] Failures identify the owning layer: UI, adapter, transport, service, or persistence.

## Explicit non-goals

- Changing the Phase 1 spaced-repetition algorithm while adding intraday entry points.
- Combining all deferred work into one implementation batch.
- Treating existing frontend enums as backend authority.
- Selecting OpenAPI, generated types, generated clients, shared packages, or a monorepo without a separate decision.
- Adding new gamification rules during runtime validation.
- Treating local commits or accepted focused evidence as pushed, reviewed, merged, deployed, or shipped.
- Updating historical plans, README files, or implementation code as part of this documentation child.
